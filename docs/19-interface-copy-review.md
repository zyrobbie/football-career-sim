## 1. 本轮边界

### 1.1 本文覆盖

- 首页与五步建档；
- 青训邀请、首次入队、半年训练、特殊事件、半年报告；
- 青训完成、职业合同、职业半年、转会与新援融入；
- 球员、履历、设置、退役决定、退役档案与图片预览；
- 全局导航、自动保存、确认框、错误提示；
- 玩家可见的角色、状态、赛事阶段、训练环境等共享术语；
- 系统生成文案的来源、动态变量和后续内容库范围。

### 1.2 本轮不改

- 俱乐部、联赛和赛事的事实名称；
- 比赛、成长、合同、转会、事件、荣誉和国家队规则；
- `GameState`、存档、版本号和数据库；
- SVG、主题、排版和部署配置。

### 1.3 文案修改风险标记

| 标记 | 含义 |
| --- | --- |
| `S` | 短按钮、导航、标签；手机端建议不超过 8 个汉字 |
| `M` | 标题或卡片说明；建议不超过 18 个汉字 |
| `L` | 正文；可以换行，但建议控制在 45 个汉字以内 |
| `D` | 含动态变量；花括号内容必须保留 |
| `T` | 共享术语；修改后必须全局统一 |
| `A11Y` | 屏幕阅读器文字或 `aria-label`；可以润色，但不能删除语义 |
| `LEGAL` | 删除、覆盖、不可撤销等风险提示；不能弱化后果 |

### 8.3 事件内容库规模

当前 `src/engine/careerEvents.ts` 含 **85 个事件定义**。事件标题、导语、两步路线、选择说明、效果预览、概率标签、即时结果和延迟后果合计约 **1,700 条中文代码级文字出现**。它们属于“剧情内容库”，不是单纯的页面框架文案。

为避免一份审核表膨胀到数千行并让修改失去上下文，本轮先冻结字段结构：

| 字段 | 玩家看到的位置 | 是否可改 | 不得改变 |
| --- | --- | --- | --- |
| `eyebrow` | 事件眉题 | 是 | 不影响分类 |
| `title` | 事件标题／选项标题 | 是 | 不改 `id` |
| `description` | 事件与选项说明 | 是 | 不改资格条件 |
| `setup.prompt` | 第一步问题 | 是 | 不改路线对应关系 |
| `effectPreview` | 选择前效果预览 | 是 | 必须与真实数值方向一致 |
| `outcome.label` | 概率结果名称 | 是 | 不改概率权重 |
| `outcomeSummary` / `summary` | 即时或延迟结果 | 是 | 必须与实际结果一致 |

产品先完成本文核心 UI 后，再从同一基线生成“85 个特殊事件逐条文案附录”。这仍属于本项目，但应作为独立审稿批次，否则无法可靠校对“预告文字是否与实际数值一致”。

## 19. 系统生成内容：第二审稿批次

以下文字会显示给玩家，但它们由规则引擎按状态生成。改写时必须逐条核对含义，不能只追求语气自然。

| 内容库 | 主要来源 | 玩家看到的位置 | 后续审稿要求 |

| 一线队通道总结 | `src/engine/firstTeamPath.ts` | 半年报告、一线队通道 | 文案必须对应真实状态枚举 |

| 合同谈判结果 | `src/engine/contracts.ts` | 首份合同、转会谈判 | 必须准确区分原报价保留与报价撤回 |

这部分不能被包装成“简单全文替换”。推荐在核心 UI 定稿后，从当前代码自动生成第二份附录并逐条审核；每条保留原文、修订稿、变量和真实触发条件。

## 20. 产品填写与回写流程

1. 产品只填写本文的“修订稿”列；不删 ID、不删动态变量。
2. 若某条无需修改，填写“保留”。
3. 若要统一改词，优先填写第 17 节共享术语，不必在每个页面重复填写。
4. 完成核心 UI 后，单独生成第 19 节所列内容库附录。
5. 代码回写时建立 `ID → 源文件 → 字符串` 对照，只改玩家可见文字。
6. 执行定向测试、全量测试、typecheck、build、数据检查、二维码检查和 `git diff --check`。
7. 使用 320×568、390×844、1280×720 检查标题、按钮、表格、卡片和确认框；不能靠缩小字体容纳长文案。
8. 对特殊事件、合同、转会、国家队和退役总结做含义回归，确认改写未与真实结算矛盾。
